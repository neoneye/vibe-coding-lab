Investigation · matrix-3way-multiplication

Is A·B·C cheaper as one three-way product?

Computing A·B·C normally means two matrix multiplications, (A·B)·C. With Strassen, that costs 7 + 7 = 14 scalar multiplications for 2×2 matrices. Can an algorithm that sees all three matrices at once do better? The answer depends on what you count as the cost.

Count scalar multiplications
No (14 stands)

A fused 3-way decomposition needs N⁴ products. Two-level schemes need 2·R(N). A search for 13 found only approximate (border) schemes.

Count EML tree size
Yes, 25 vs 33

x·y·z is much shorter as one exp−ln tree, but that tree contains no multiplications at all. It is the log-table trick.

Writes expensive, reads free
Yes: N² vs 2N²

Fusing the chain writes only the outputs, with no extra arithmetic if one column of B·C fits in registers.

Repeated values, cache products
Yes: ≤ k² + k³

With k distinct values, a fused triple table makes the multiplication count independent of N, at the price of N⁴ additions.

1 · Fused 3-way products: rank exactly N⁴

Pair the output with a fourth matrix D. Then A·B·C is the 4-linear form TN(A,B,C,D) = trace(ABCD) = Σ AijBjkCklDli. A "3-way algorithm" writes TN as a sum of R terms, each a product of three linear forms (one each in A, B, C) scattered into the outputs. The (A,C | B,D) flattening sends every index tuple (i,j,k,l) to its own column, so it is a permutation-like 0/1 matrix of rank N⁴. Tensor rank (and border rank) is at least any flattening rank, and the naive algorithm uses N⁴ terms. So R(TN) = N⁴: 16 for 2×2, worse than the Strassen chain's 14.

(A,B | C,D) flattening: only depends on the products AB and CD.
(A,C | B,D) flattening: one 1 per row and per column, so full rank.

Two-level schemes can only tie the chain

Suppose level 1 computes s products ℓ(A)·m(B), and level 2 multiplies t combinations of those by forms c(C). The span of the level-1 products must contain the four forms (AB)ij, so s ≥ R(⟨N,N,N⟩). By symmetry t ≥ R(⟨N,N,N⟩). The chain attains both bounds. At N = 3, beating 46 here would mean 3×3 matrix multiplication in fewer than 23 products, a famous open problem.

Two chained Strassen steps compute A·B·C with exactly 14 multiplications. This is also proved in Lean (lean/Chain.lean, core Lean 4, grind).

2 · The search for 13 multiplications

The next model is broader: any circuit whose gates have degree ≤ 3, where linear forms may mix entries of A, B and C, which allows Winograd-style commutative tricks. The 6 + 7 near-hits are not algorithms. Under ridge continuation (minimise fit² + μ‖p‖² while μ → 0) the error falls only as the coefficients diverge, with residual roughly ∝ ‖p‖⁻³. That is the signature of an order-1 border decomposition: each product carries three ε−1/3 factors, the 1/ε terms cancel, and an O(ε) error remains. The same thing happens for A·B alone. 6 commutative products approximate 2×2 A·B arbitrarily well, but an exact algorithm needs 7 (Winograd 1971). So the "13" is just a border-6 A·B followed by the ordinary 7 for ·C, which is not a 3-way effect.

3 · EML trees: x·y·z costs 25, not 33

Odrzywołek showed that eml(a,b) = exp(a) − ln(b) together with the constant 1 generates every elementary function. His direct search found x·y at RPN length 17. An exhaustive search written for this page reproduces his values (x−y 11, −x 15, 1/x 15, x² 17, x·y 17). The x·y tree is a log-domain accumulator: s = e − ln x, then s ← eml(ln s, y) = s − ln y, then exp(e − s). Each additional factor costs 8 tokens, giving 8n + 1 instead of 16(n−1) + 1 for nested trees.

Evaluated live in complex arithmetic (principal branch, ln 0 = −∞). Negative inputs work because the branch jumps cancel inside exp.

Why this doesn't help the matrix question. The EML tree has no multiplications in it: it is exp(ln x + ln y + ln z), and the saving is just dropping the exp→ln round trip between the two factors. In EML, products are cheap and addition is expensive (x+y needs 19 tokens). Each entry of A·B·C is a sum of four triple products, so the EML cost is dominated by additions.

4 · When writes are expensive and reads are free

This is the setting of non-volatile and asymmetric memory. Reads cost nothing, every word written to memory costs one, and a small scratch area of S registers is not counted as memory. The N² outputs must be written, so W ≥ N². Here three-way fusion does pay off: the intermediate A·B never has to be stored. Every schedule below runs in your browser, instrumented and checked against a direct product.

Total = ω·writes + operations, where operations are multiplications, or exps in the e/ln domain. The cheapest row is highlighted. Strassen rows use temporaries written to memory, the setting of Carson, Demmel et al., who proved Strassen-like algorithms cannot be write-avoiding.

Which memory words get written (N = 4)

  • Column fusion: hold column l of B·C in N registers, then compute D[:,l] = A·(B·C)[:,l]. That gives W = N² with exactly the chain's 2N³ multiplications.
  • With fewer registers: S output accumulators and recomputed B·C entries give N³ + N⁴/S multiplications, still at W = N². This beats the chain whenever ω > N²/S − N.
  • e/ln domain: a triple product is one exp of a sum of three logs. The fully fused sum then costs N⁴ exps with a single register. At N = 2 that is 16, a tie with the chain, but with half the writes and no scratch. Logs are recomputed on every read, which is free here; storing them would cost 3N² writes.

5 · Repeated values: caching products

If the matrices contain only k distinct values, the same scalar products recur and can be cached. Quantised neural-network weights (4-bit means k = 16) and ternary weights are examples. A cache keyed by value pair is the same thing as grouping by the distributive law: Dil = Σa a · (Σj : Aij=a (BC)jl) needs one multiplication per distinct value in the row. Four schedules, each instrumented and checked against the exact product:

  • chain, no cache: 2N³ multiplications.
  • chain + product cache: memoise a·b, then t·c. The intermediate A·B has many distinct values, but each one meets only k values of C, so the second stage costs about N²k. In effect the cache performs the grouping automatically.
  • pair cache + grouping, A·(BC): at most k² products for B·C, then one multiplication per distinct value in each row of A. That is ≈ k² + N²k with a table of only k² entries.
  • fused triple table: cache each value triple a·b·c once. The output is then pure additions, and the multiplications number at most k² + k³ whatever N is. This is the genuinely three-way effect, but it costs N⁴ additions instead of ≈ N³.

What this shows

  • Caching a product is the same as grouping equal values. For example, a·x + a·y = a·(x + y) needs one multiplication instead of two.
  • The ordinary chain benefits more than expected. Each entry of A·B meets only k different values of C, so a cache brings the chain down to about k² + N²k multiplications. That needs no three-way method.
  • The genuinely three-way effect is the fused triple table. Compute every a·b·c once, then build the result by additions alone. That is at most k² + k³ multiplications however large N is (80 at k = 4, against 65,536 for the plain chain at N = 32).
  • The price is additions: N⁴ instead of about N³. Compared with grouping, the triple table saves multiplications only when k < N (k³ < N²k). It is worth it only where a multiplication costs far more than an addition.
  • With all-distinct values, caching gains nothing, and the triple table is the worst option (N³ + N⁴ multiplications).
  • In the write-expensive setting of section 4, the cache itself costs writes unless it fits in scratch. The k² pair table usually fits; the k³ triple table may not.

This idea is well established for two-matrix products: the Four Russians method for Boolean matrices, the Mailman algorithm for small alphabets, and lookup-table kernels for quantised LLMs (LUT-GEMM, T-MAC). The triple-table trade-off for three factors was not found written up anywhere.

Prior work, and how these results compare

Three-way matrix products have been studied from several directions. Most of what this page finds either restates known theory for the chain tensor or rediscovers established practice. The table puts each result next to the closest published one.
