# MOS 6510 — standalone emulator page

Date: 2026-09-17
Directory: `mos-6510/`

## Goal

A dependency-free `index.html` that teaches the MOS 6510 — the CPU in the
Commodore 64 — by letting the reader assemble small programs, step them one
instruction at a time, and watch the machine state change. Same genre and visual
language as `intel-4004/`: a live block diagram, register file, memory view,
disassembly with breakpoints, execution trace, and an assembly workbench with a
demo library.

The 4004 page is an instruction-level playground, not a gate-level model. This
page keeps that contract.

## Scope

**In:**

- Full 6510 core: 151 documented opcodes plus the stable undocumented ones
  (LAX, SAX, DCP, ISC, SLO, RLA, SRE, RRA, ANC, ALR, ARR, SBX, NOP variants),
  JAM as a real halt.
- Cycle counts including page-cross and branch-taken penalties.
- The `JMP ($xxFF)` indirect page-wrap bug, and zero-page index wrap.
- Decimal mode for ADC/SBC (the 6510 has it; the C64 KERNAL barely used it).
- 64 KB RAM. No KERNAL, BASIC, or character ROM — those are Commodore
  copyright and are not shipped.
- The 6510's on-chip 6-bit I/O port at `$00` (direction) and `$01` (data),
  the one thing that is not a 6502.
- A VIC-II subset: 40x25 screen RAM at `$0400`, colour RAM at `$D800`,
  border `$D020`, background `$D021`, raster counter `$D012` + `$D011` bit 7,
  advancing on PAL timing (63 cycles/line, 312 lines/frame).
- An original hand-drawn 8x8 character set approximating the C64 uppercase
  charset, plus reverse video via bit 7 of the screen code.
- Assembler, 8-program demo library, undo, breakpoints, trace.

**Out:** SID, CIA timers and IRQs, sprites, bitmap modes, sprite/raster IRQ,
disk/tape, and the unstable undocumented opcodes (ANE, LXA, SHA/SHX/SHY/TAS) —
those depend on analog chip behaviour, so any value shown would be fiction.
They decode and then stop the machine with an explanation rather than lie.

## Architecture

One `index.html`. Engine lives in `<script id="shared-code">` so `test.mjs`
can load and run it under Node, following the `game-snake/` convention.

Units inside the shared block, each independently testable:

1. `OPCODES` — a 256-entry table: mnemonic, addressing mode, base cycles,
   page-cross penalty flag, legal/illegal/unstable classification.
2. `disassemble(bus, pc)` — returns `{ bytes, size, text, mode, target }`.
   Pure; used by the listing, the trace, and the block diagram.
3. `Bus` — 64 KB RAM plus the I/O overlay: `$0000/$0001` processor port,
   `$D000-$D02E` VIC registers, `$D800-$DBFF` colour RAM (low nibble only).
   Every write is journalled so undo does not need 64 KB snapshots.
4. `CPU6510` — registers, flags, `step()` returning a description record
   (`{ pc, text, detail, cycles, group }`) used by the explanation strip.
5. `assemble(source)` — two-pass assembler. Labels, `*=` / `.org`, `.byte`,
   `.word`, `.text "..."` (raw bytes), `.screen "..."` (screen codes),
   `<label` / `>label` lo/hi, `$hex`, `%binary`, decimal, `label+n`.
6. `Video` — screen RAM + colour RAM + border/background into an ImageData
   buffer; the font table lives here.
7. `SixtyFiveTenTests` — the test suite, run from `test.mjs`.

UI code sits in a second, untested `<script>`: DOM wiring, render loop,
canvas blit, keyboard shortcuts.

## Data flow

Assemble → `{ rom bytes, entries, labels, entry }` → written into `Bus` RAM →
`CPU6510.reset()` sets PC from the reset vector at `$FFFC` (the assembler
writes it, defaulting to the first `*=` address). The run loop spends a cycle
budget per animation frame; each `step()` advances the raster counter by the
instruction's cycles. Render reads state and repaints; the canvas repaints
every frame while running, on demand while paused.

## Undo

A per-step journal of `{ address, previousValue }` writes plus a copy of the
register set. 512 steps deep. Cheaper and more honest than snapshotting RAM.

## Error handling

- Unknown/unstable opcode: pause with a message naming the opcode and why.
- `JAM`/`KIL`: pause, described as the real lock-up it is.
- Assembler errors: line number, what was expected, what was found.
- Branch out of range, address too large, overlapping origin: all caught at
  assemble time with the offending line.

## Demo library (8, ordered)

1. **First poke** — store a character and a colour, nothing else.
2. **Addressing modes tour** — the same value reached eight ways.
3. **Loop and index** — fill a screen line with `LDX`/`STA abs,x`/`INX`/`BNE`.
4. **The 6510 port** — write `$00`/`$01`, watch the direction bits and the
   bank readout; explains what these lines do on a real C64.
5. **16-bit add** — `CLC`/`ADC` across two bytes, carry made visible.
6. **Subroutines and the stack** — `JSR`/`RTS`, `PHA`/`PLA`, stack panel.
7. **Raster wash** — poll `$D012`, write `$D020`; colour bars from software.
8. **Scroller** — shift a screen line left each frame, feeding characters from
   a message; the showy one, still only 30 lines of assembly.

Each carries a title, tag, description, and a "what to watch" note.

## Testing

`test.mjs` extracts the shared-code block and runs `SixtyFiveTenTests.run()`.
Coverage:

- Flag behaviour for every ALU op, including overflow's four cases.
- Decimal mode ADC/SBC against known-good values.
- Every addressing mode's effective address, including zero-page wrap,
  `(zp),y` page cross, and `abs,x` page cross cycle penalty.
- The `JMP ($xxFF)` bug.
- Branch cycle penalties: not taken, taken same page, taken across a page.
- Stack wrap at `$0100`.
- Each stable illegal opcode against its documented composite behaviour.
- Assembler: each addressing mode, lo/hi operators, forward labels,
  branch-range errors, and a round trip assemble → disassemble.
- Bus: processor-port read-back through the direction register, colour RAM
  masking to 4 bits, raster counter advance.

## Non-goals

Not a C64 emulator. It will not run a `.prg` that calls the KERNAL, because
there is no KERNAL. The page says so plainly in its limitations panel.
